Who Can Call receiveMessage for a CCTP Mint?

The destinationCaller field names who may call receiveMessage for a CCTP mint. Set it to zero for open relaying or a bytes32 address for one caller.

Crypto Daybook NewsroomNov 28, 2026 · 05:11 UTC3 min read

The destinationCaller field decides who can submit the attested message to mint USDC on the destination chain. A zero value lets anyone call; a specific address limits the call to that address. This setting matters when a USDC bridge transfer needs a contract to act as soon as the funds arrive.

For a plain transfer, an open caller can make it easier for a relayer to complete the mint. For a transfer that must trigger a follow-up action, a USDC bridge can use a contract as the named caller so it can handle the minted USDC in the same transaction.

How the caller check controls the mint

At burn time, TokenMessenger writes destinationCaller into the message as a bytes32 value. Circle’s attestation signs that message, so the value cannot be changed after the burn.

On the destination chain, MessageTransmitter checks the message before it accepts receiveMessage. It compares the caller’s address, msg.sender, with the signed value. A zero value passes the check for any caller; a non-zero value passes only when the caller matches.

  • Zero bytes32: Any address may submit the message and complete the mint.
  • A specific address: Only that address may call receiveMessage for this burn.
  • An address that cannot call: The check will keep reverting, leaving the USDC unminted.

Say an app burns USDC on Ethereum and sets its Base contract as destinationCaller. Once the attestation is ready, that Base contract must call receiveMessage. The mint then delivers USDC to its chosen recipient, and the contract can deposit those funds into an app in the same transaction. A third-party relayer cannot submit the message on its behalf.

That restriction means the named caller needs a way to make the destination call and pay its gas. If it never submits receiveMessage, the mint does not happen. For a normal wallet transfer with no contract action to run afterward, setting the field to zero leaves completion open to any relayer.

Encode the intended EVM address as bytes32 when setting a specific caller. In CCTP V1, the caller setting is exposed through depositForBurnWithCaller. In CCTP V2, it is a parameter to depositForBurn. Circle’s CCTP developer documentation describes the parameter; the MessageTransmitter.sol contract in circlefin/evm-cctp-contracts shows the caller check.

Related questions

depositForBurn vs depositForBurnWithCaller

In V1, depositForBurnWithCaller is the option that sets a specific destination caller. In V2, depositForBurn takes destinationCaller as a parameter, so the caller choice is part of that burn request. In either version, zero leaves receiveMessage open to any caller.

Who pays gas for the CCTP mint on the destination chain?

The address that submits receiveMessage pays the destination transaction’s gas. With a non-zero caller, that must be the named address; with zero, a relayer or another willing caller can submit and pay.

Putting the caller setting into practice

Can a CCTP burn be replaced after the destinationCaller was set wrong?

Do not assume you can edit the caller on an existing burn: it is inside the attested message. Check whether the specific CCTP version and integration support replacing or cancelling that deposit. Otherwise, the named address must call receiveMessage; if it cannot, that message cannot pass the caller check.

How do CCTP V2 hooks differ from using destinationCaller with a wrapper contract?

destinationCaller controls who submits receiveMessage. A hook carries instructions for an automated action on the destination after assets arrive. A wrapper contract can be named as caller and handle a mint followed by its own deposit logic, while a hook provides CCTP’s built-in route for chaining destination actions. Choose based on whether you need to control the submitter, run an arrival action, or both.
